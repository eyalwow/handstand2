## Architecture direction — future iOS/Android apps (2026-10-27)
- User intends Apple App Store and Google Play distribution. - Apply boundaries incrementally while working on requested features: UI renders state and handles user actions; analysis consumes timestamped pose/frame data and returns versioned results without DOM, storage or HTTP dependencies; storage repositories own reads/writes/migrations; API clients own server communication. Platform adapters own media selection/capture, file access and app lifecycle. Existing inline analyzer code is not yet fully extracted; this is the required direction for subsequent refactoring, not a claim that separation is complete.
- Retain local-first saving and all existing data/keys for now. Introduce asynchronous repository interfaces at the storage boundary when changing it, so a native persistent store or Supabase implementation can be added without coupling screens to a provider. Keep current recovery, quota handling, active-session persistence and idempotent finish behavior.
- Future data contract: stable client-created UUIDs for new session/analysis records, schemaVersion, UTC createdAt/updatedAt, optional ownerId, and separate analysisVersion/scoringVersion. Keep exercise IDs and completed-set identity stable; use explicit duration units and distinguish unobserved values (null) from measured zero. Add fields through backward-compatible, tested migrations rather than rewriting current saved records. Ownership is assigned by authenticated server rules later, never trusted merely because a client supplies ownerId.
- Future sync: an optional auth adapter and repository sync layer, preserving anonymous/offline use. Plan idempotent upserts by record ID, queued offline mutations, deletion tombstones and explicit conflict handling. Never silently merge concurrent active workouts or overwrite local guest history on sign-in. Define guest-history import and account-switch isolation before introducing accounts; no sync/account system is implemented now.
- Keep Gemini credentials server-only and consent behavior intact. A packaged client will need an explicit configurable HTTPS API origin rather than assuming relative /api routes. Review trusted native/web origins, CORS and authorization at that stage; do not solve native access with unrestricted origins or embedded API keys.
- Native video/MediaPipe is a release gate, not guaranteed by browser tests. Before choosing a wrapper, test the existing pipeline on real iOS WKWebView and Android System WebView with representative devices: WASM/model asset loading, GPU/WebGL availability and fallback, codec/container support, portrait rotation, native file-to-decodable-media conversion, frame timestamps/seeking, memory limits and background/resume recovery. Isolate runtime loading/frame extraction behind adapters; bundle required runtime/model assets when appropriate. If a WebView cannot meet correctness/performance requirements, evaluate a native analysis adapter while preserving the result contract and UI.

- Scoring policy: 70% hold / 30% ascent when both qualify; weights are renormalized when only one phase is observed. A conservative ascent gate requires a visible supported-to-inverted transition, sufficient duration/coverage and joint visibility. Already-held, missing or uncertain entry footage is not scored as a failed ascent. Unavailable entry arch is excluded instead of receiving a perfect default.
