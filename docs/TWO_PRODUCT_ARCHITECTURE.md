# Handstand Lab + Handstand Coach — initial direction

One repository and shared domain infrastructure, two independently deployed frontends. This is a direction, not a completed migration. `vercel-app/` remains the athlete app. `coach-app/` is a dependency-free, synthetic-only coach prototype with no backend access. Do not copy the analyzer or exercise catalogue into it. The athlete app and existing local storage keys are untouched.

As features require it, extract shared domain modules for exercise IDs/catalogue, program versions/prescriptions, workout events and versioned analysis results; UI-independent analysis; async repository interfaces (existing local adapter first); API client and platform/media adapters. Both interfaces will consume these modules. Do not duplicate calculations in each product. Athlete native packaging remains a future Capacitor candidate requiring real-device video/WASM tests. Coach starts on Web; packaging later need not change domain contracts.

Future Supabase: one Auth identity, optional athlete and coach capabilities (a person may have both), not mutually exclusive account types. Proposed entities: profiles, coach_athlete_relationships, programs, program_versions, assignments, workout_sessions, set_events, analysis_results, analysis_grants and coach_comments. UUIDs, UTC timestamps and schema/analysis/scoring versions. Athlete records remain athlete-owned; program assignments reference immutable versions. An independent athlete can later connect to a coach without replacing history. No schema, account system or cloud migration is provisioned here.

Before real data: default-deny RLS on every private table and storage bucket; owner access plus explicitly active coach relationship AND a grant for the resource/scope. A coach role alone grants no athlete access. Verify grant/relationship ownership server-side. Revocation blocks subsequent reads/writes, subscriptions and signed-media access; use short-lived URLs, clear client caches, and disclose that already downloaded copies cannot be recalled. Test cross-coach isolation, guessed IDs, expired/revoked grants and account switching. Never expose service-role or Gemini keys in clients. Keep shared exercise content independent of any one coach's ownership.

Future sync preserves guest data via explicit import, stable IDs, idempotent writes, offline queue and conflict policy. Coach feedback is distinct from AI output; record author and version. AI assists professional review. Handstand entry detection and overall-grade calibration remain unverified as recorded in PROJECT_STATUS.md. Do not market the engine as proven.

Prototype routes: #dashboard, #athletes, #athlete/demo-noam, #programs, #program/balance, #analysis/demo-noam. Search, profile links, plan details, temporary coach notes and simulated athlete consent/revocation work in memory only. Refresh resets everything. All analysis text/scores are fabricated and labeled, never a live Gemini response. The consent toggle is an explicitly labeled simulation of an athlete action, not a future coach permission.

Next gate: review this limited prototype before adding backend, accounts or more features. No billing, paid services, real users or production release authorized.

## Working local prototype (v2)

`store.js` is the local repository/domain boundary; `app.js` only renders and dispatches commands. The shared catalogue remains `vercel-app/exercise-library.js`: `catalog.js` re-exports it in source; `build.mjs` packages the canonical file inside the coach-only static output. No trainee source is modified. No analysis engine is copied into the coach application.

Local schema 2 uses its own key `handstand-coach-demo-v2`. Programs hold append-only versions. Assignments reference a program/version and are immutable records; later reassignment does not rewrite sessions. Sessions retain prescription snapshots, unique IDs, source assignment/workout index and timestamps. Active sets persist separately and complete into history once. Program deletion is explicit archival: assigned history stays readable. No automatic inference from completion frequency to health or readiness.

Transactions clone/validate first, compare the persisted revision to detect stale tabs, then publish in-memory state only after localStorage succeeds. Failed writes show errors and keep previous data. Corrupt storage blocks mutation until explicitly confirmed reset; it is never silently replaced. Reset touches only the coach key. This prototype has no server-side access control; simulated sharing is UX only.

Future migration must distinguish synthetic from real records. NEVER upload these demo fixtures into real athlete accounts. Offer an explicit disposable demo reset. Guest trainee data needs a separate, user-consented import flow: retain original local backup, assign stable UUID mapping, validate schema, perform idempotent server transactions under authenticated ownership, verify counts/checksums, then mark imported. Never clear local history before confirmed server persistence. Conflicts and account switches must not cross users.

Suggested Supabase relationships: profile (auth subject), capabilities (coach/athlete, many per subject), coach-athlete links (invited/accepted/revoked), athlete-owned sessions/results, coach-owned program definitions with immutable versions, scoped athlete-issued analysis grants and comments tied to their author. RLS checks must validate the authenticated user on BOTH relationship ends and a currently active scoped grant. Test SELECT/INSERT/UPDATE/DELETE, joins, storage URLs and realtime, including coach A versus B and revoked access. Preserve historical authorship while preventing new access after revocation. No service-role keys in apps. Backend implementation and RLS tests remain prerequisites before any real information is connected.

Comparison policy: sessions are comparable only within the same assignment, immutable version and workout index. Current UI compares completed-set counts only, with no claim about technique. Weekly counts are computed from persisted finished timestamps; completion percentage uses full sessions / assigned weeks × days, capped at 100. Partial sessions remain in history but do not count as full completions. These are administrative summaries, not AI conclusions.
